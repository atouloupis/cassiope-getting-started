5 · Connexion interne entre applications

Les variables {PRÉFIXE}_URL, _HOST et _PORT injectées par un lien interne sont détectées ici.

Comment tester une adresse interne, et prérequis
  1. Déployez une seconde copie de ce service (le producteur) dans la même machine que celle-ci : deux ressources ne se connectent que si elles tournent sur le même nœud.
  2. Dans le producteur, onglet Connexions : Exposer avec le port 3000 (ou celui de PORT), portée internal (même projet) ou tenant. Le service est redéployé.
  3. Dans ce service (le consommateur), onglet Connexions : Connecter le producteur avec un préfixe, par exemple API. Trois variables sont injectées au prochain déploiement : API_URL, API_HOST, API_PORT.
  4. Redéployez le consommateur : les variables ne sont lues qu'au démarrage. Le lien apparaît alors ci-dessous : cliquez sur Tester.

Un test réussi affiche la réponse du producteur, dont calledBy = le nom de ce service. Un délai dépassé signale le plus souvent deux services sur des nœuds différents ou un producteur non redéployé après l'exposition ; un refus de connexion, un mauvais port exposé.

7 · Configuration avancée : ports et healthcheck

Testez le comportement de Cassiope face à un service qui change de port ou devient malsain. Les pannes simulées se désarment seules.

Healthcheck /healthz

Attendu : un service configuré avec un healthcheck est marqué malsain après quelques échecs ; sans healthcheck, rien ne change. Voir la page du service pour l'état affiché.

Ports

Le service écoute sur PORT (3000 par défaut). Pour tester un autre port : changez PORT puis le port exposé dans Cassiope, ou ajoutez EXTRA_PORTS=8081,8082 pour écouter sur plusieurs ports, puis exposez l'un d'eux. Le bloc ci-dessus indique le port et l'hôte vus par l'application.
